This document reconstructs the system from first principles: not what each file is called, but why the request is shaped the way it is — where identity is established, where the one real security boundary sits, why a question about several companies fans out and reconverges, and why a groundedness check is allowed to fail open. Every box below maps to a real function in backend/src/; nothing here is aspirational.

§1 End-to-end request lifecycle

Two lanes run through this system. The top lane runs once, offline, and turns PDFs into searchable, access-tagged chunks. The lower lane runs once per chat turn, and is where every architectural decision that matters — identity, isolation, filtration, grounding — actually happens. Both lanes converge on one shared datastore.

§2 Identity, and the security-critical divergence

Login is intentionally shallow: DUMMY_USERS is a static in-code dict mapping an email to a list of company_ids — no password, matching the assignment's "dummy login" requirement. The JWT it issues carries three claims: sub (email), companies, and exp (60 minutes out), HS256-signed.

The interesting decision isn't the login — it's what happens after. The two authenticated routes diverge deliberately in how much they trust that token:

A

/api/query — trusts the token

Decodes the JWT and passes payload.companies straight into retrieve(). Simple, and correct for the token's full 60-minute life — this endpoint is a retrieval-only debugging primitive, not the production surface.

B

/api/conversations/{id}/messages — re-derives it, every time

Uses the JWT only for the email identity claim, then calls get_user_companies(current_user.email) fresh against config/users.py on every single request. A JWT is valid — signature intact, not expired — for up to 60 minutes after login. If DUMMY_USERS changes mid-session, a route trusting the cached claim would keep honoring stale permissions until the token expires. Re-deriving closes that window: access changes take effect on the next request, not the next login.

backend/src/api/routes/chat.py — send_message, send_message_stream

This is the more conservative of the two designs, and it's the one the assignment's isolation tests are graded against — a "still-valid-but-revoked" JWT is exactly the attack a real access-control system has to defend against, and this is the one place it's handled correctly.

§3 Orchestration as a state machine

The conversational path is a langgraph.graph.StateGraph(ChatState) — every node is a pure function ChatState → dict, and LangGraph merges each node's returned keys into one running state object threaded through the whole turn. Only classify branches; every other edge is fixed.

1

classify — one fast LLM call, temperature 0

Routes to greet, deny, or continue. Its own prompt says explicitly that this is UX shaping, not a security control — the point is to skip a wasted retrieval+generation round trip on small talk, not to gate access.

2

rephrase — turns a follow-up into a standalone query

Retrieval has no memory of the conversation, so "what about their margins?" has to become a self-contained question before it's embedded. Skipped entirely (no LLM call) on the first turn of a conversation.

3

decompose — one sub-question per named company

A question naming several companies becomes sub_queries: list[dict], one entry per company (or a single general entry). This is what makes the fan-out in §5 possible.

Why an LLM classifier instead of a keyword router? Earnings-call questions take too many phrasings for regex to catch reliably — a rules router either over-triggers deny on legitimate but unusual phrasing, or misses adversarial rephrasings built to evade a fixed keyword list. The cost is one extra call per turn, kept cheap by a short prompt at temperature 0.

§4 Filtration — where authorization actually happens

This is the one design decision the whole system hinges on: filtering happens inside the approximate-nearest-neighbor search, not after it. An unauthorized chunk is never fetched, never ranked, never even considered a candidate — as opposed to running search unfiltered and discarding disallowed hits afterward, which wastes ranking budget and creates a bug class where someone forgets the post-filter step.

§5 Parallel fan-out for multi-company questions

"Compare TCS and Infosys margins" names two companies. Rather than answer half the question or run two round trips back-to-back, decompose_node splits it, and LangGraph's Send API dispatches one fetch_one / answer_one branch per company as a genuinely concurrent graph execution — this is dynamic map-reduce, not a for-loop.

§6 Generation, citations, and a guardrail that fails open

1

Prompt assembly

Every retrieved chunk becomes one line: [{chunk_id}] ({company_id}, {fiscal_quarter} {fiscal_year}, {speaker_name}): {text}. The answer prompt instructs the model to cite every factual claim with its bracketed chunk_id immediately after the claim, answer strictly from the provided context, and say plainly when context is insufficient rather than guess.

2

No-context short-circuit

If a company's fetch_one returned zero chunks — because the user isn't authorized, or nothing matched — NO_CONTEXT_MESSAGE is returned directly, with no LLM call made at all. This both saves cost and guarantees a company with zero authorized chunks can never leak through a model's outside knowledge — filtration is reinforced at the generation layer, not just the retrieval layer.

3

Citation selection

A chunk counts as "cited" if its chunk_id literally appears in the generated text. If the model cites nothing, the first three retrieved chunks become the citations instead of showing none.

4

guardrail — a second LLM call, checking the first one's output

Verifies two booleans against the same context: grounded (every claim traceable, no fabrication) and safe (doesn't follow instructions smuggled in via transcript text or a crafted question — a prompt-injection defense). It fails open on three conditions: disabled by settings, no chunks to check against, or its own call throwing. This is deliberate — the guardrail checks answer quality, not access; access is already enforced deterministically upstream (§4), so failing open here can degrade an answer's polish but can never reopen an authorization hole.

§7 Persistence and cross-user isolation

Conversation history lives in one MongoDB collection, but the isolation guarantee is structural, not a query clause: every document's _id is the composite string f"{user_email}::{conv_id}". Two users literally cannot address the same document, even if a conv_id were reused — there's no shared mutable state between requests, so concurrent sessions can't collide.

get_full_thread goes one step further and re-checks doc.user_email == email even though the _id scheme already namespaces the lookup — a belt-and-suspenders IDOR guard that's the one line that would actually stop cross-user thread access if the ID scheme were ever "simplified" later without noticing this dependency. send_message calls this before any retrieval or LLM call, so a guessed or leaked conv_id is rejected with a 404 up front.

§8 Output: blocking JSON vs. streamed SSE

The blocking endpoint runs the compiled graph via graph.invoke() and returns one JSON object. The streaming endpoint (stream_chat_graph_answer) can't use .invoke() — LangGraph doesn't interleave node execution with token-level streaming of one specific node's call — so it calls the same node functions directly, by hand, and streams the answer-generation call's tokens as delta events.

The guardrail still needs the complete answer to judge groundedness, so it only runs after the last token, and the trailing done event carries the authoritative answer. If the guardrail rejects, done.answer differs from the concatenated deltas the client already rendered — clients must treat done as authoritative and replace, not append. Both endpoints persist the user + assistant turns only after the response is fully produced, so a client that disconnects mid-stream never leaves a partial turn written to history.

§9 How the filterable data got there

The filtration in §4 only works because company_id is assigned once, at ingestion, and never re-derived anywhere else. chunker.py segments each transcript by who is speaking — a Q&A marker splits the document into prepared_remarks / qa sections, recurring speaker names (≥2 occurrences) become turn boundaries, and each analyst turn opens a new qa_pair_id that stays attached to the management turns answering it. (A cover-letter preamble before the first recognized speaker becomes its own untagged turn.) The resulting company_id/doc_id becomes the exact join key the access-control filter uses at query time — ingestion and security share one identifier scheme by construction, not by a convention that could drift.
